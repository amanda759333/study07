# PRD: 팀 편성 웹 앱

학생이 스스로 팀을 편성하고, 마감 뒤 남은 학생은 AI가 배정하며, 앱이 AI의 답을 규칙으로 검사하는 Streamlit 앱.

- 근거 문서: 「중간 과제 공고: 팀 프로젝트를 위한 팀을 편성하는 웹 앱 만들기」(이하 공고)
- 출처 표기: 요구사항마다 `[공고 2.4]`처럼 공고의 절 번호를 단다. 절 안의 표 행이나 항 번호가 있으면 함께 적는다
  (예: `[공고 2.4 「팀이 꽉 참」]`, `[공고 2.5-2]`)
- 요구사항 번호: `R-역할-번호`. U = 등장인물, T = 팀 규칙, A = 지원, V = 투표, C = 마감, G = 배정
- 이 문서에 없는 것은 공고를 따른다. 공고와 이 문서가 다르면 공고가 맞다

## 2. 팀 규칙

| 번호 | 요구사항 | 출처 |
| --- | --- | --- |
| R-T1 | 관리자가 명단을 올릴 때 넣은 팀 수만큼 팀을 만든다(팀1, 팀2, …) | 공고 2.3 「팀」 |
| R-T2 | 마감 뒤 확정한 팀 구성에서는 모든 팀이 2~4명이어야 한다(빈 팀 없음) | 공고 2.3 「인원」 |
| R-T3 | 주 역할이 동일한 학생이 한 팀에 2명 이상이면 안 된다 | 공고 2.3 「주 역할 중복」 |
| R-T4 | 확정한 팀 구성에서 모든 팀에는 기획자 역할 학생과 웹 프로그래머 역할 학생이 **서로 다른 사람으로** 1명씩 있어야 한다. 주 역할이나 보조 역할로 맡을 수 있다 | 공고 2.3 「필수 포함 역할」 |
| R-T5 | 주 역할은 팀 안의 중복을 따지는 기준이고, 보조 역할은 필수 포함 역할을 맡을 수 있는지 따질 때만 쓴다 | 공고 2.3 아래 설명 |
| R-T6 | 팀 정원은 4명이다. 4명인 팀에는 지원할 수 없다 | 공고 2.4 「팀이 꽉 참」, 5장 `slot_no (1~4)` |

R-T5의 예: 주 역할이 테스터이고 보조 역할이 기획자인 학생은 그 팀의 기획자를 맡을 수 있다. `[공고 2.3]`

지원과 투표를 하다 보면 필수 포함 역할을 지킬 수 없는 팀이 생길 수 있다. 예를 들어 웹 프로그래머를 맡을 수 있는
학생이 한 명도 없이 4명이 다 찬 팀은 더 학생을 넣을 수 없고, 마감 뒤 배정에서도 기존 팀원을 옮기지 않으므로
끝까지 웹 프로그래머를 채우지 못한다. `[공고 2.3]` → 이를 막는 규칙이 R-A8이다.

### 2.1 필수 포함 역할을 채운 수 세기

R-T4와 R-A8에서 "필수 포함 역할을 몇 개 채웠는가"는 다음처럼 센다. `[공고 3장 「필수 포함 역할 자리 계산」]`

- 기획자와 웹 프로그래머는 서로 다른 학생이 맡아야 하므로, 한 학생이 둘 다 할 수 있어도 **하나로만 센다**
- 즉 "팀원 가운데 서로 다른 두 사람을 골라 한 명은 기획자, 한 명은 웹 프로그래머를 맡길 수 있는가"를 따진다.
  채운 수는 0, 1, 2 가운데 하나다
- 예: 주 역할이 기획자이고 보조 역할이 웹 프로그래머인 학생 혼자만 있는 팀은 2개 가운데 1개만 채운 것이다

## 3. 지원과 투표

### 3.1 지원

| 번호 | 요구사항 | 출처 |
| --- | --- | --- |
| R-A1 | 빈 팀에 지원하면 투표할 팀원이 없으므로 **바로 승인**된다 | 공고 2.4 「빈 팀에 지원」 |
| R-A2 | 팀원이 있는 팀에 지원하면 **대기**가 된다. 그 팀의 팀원 모두가 투표한다 | 공고 2.4 「팀원이 있는 팀에 지원」 |
| R-A3 | 한 학생은 지원한 팀의 결과(승인 또는 거절)가 나오기 전에는 다른 팀에 지원할 수 없다. 결과가 나온 뒤에는 다른 팀에 다시 지원할 수 있다 | 공고 2.4 「한 학생의 지원」 |
| R-A4 | 4명인 팀에는 지원할 수 없다 | 공고 2.4 「팀이 꽉 참」 |
| R-A5 | 주 역할이 중복되는 팀원이 있는 팀에는 지원할 수 없다 | 공고 2.4 「같은 주 역할」 |
| R-A6 | 이미 팀이 있으면 다른 팀에 다시 지원할 수 없다 | 공고 2.4 「이미 팀이 있음」 |
| R-A7 | 모집이 마감되면 지원할 수 없다 | 공고 2.4 「막힌 지원」, 2.5-1 |
| R-A8 | 지원자가 들어간 뒤 남는 자리 수가 그 팀에서 아직 채우지 못한 필수 포함 역할 수보다 적으면 지원을 막는다(어려운 해결을 고른 경우) | 공고 2.4 「막힌 지원」, 3장 「필수 포함 역할을 지킬 수 없는 팀」·「필수 포함 역할 자리 계산」 |

R-A8의 예: 테스터와 발표자만 있는 팀(2명)에 보고서 작성자가 지원하면, 남는 자리 1개로 필수 포함 역할 2개를 채울 수
없으므로 막는다. `[공고 3장]`

| R-V6 | **승인 직전 검사**: 모든 팀원이 찬성해 승인하려는 때에 규칙(정원, 주 역할 중복, 필수 포함 역할 자리)을 다시 검사하고, 어기게 되면 그 지원은 거절된다 | 공고 2.4 「승인 직전」 |
| R-V7 | 처리 순서는 지원한 순서가 아니라 **투표가 끝난 순서**다 | 공고 3장 「같은 팀에 대기 중인 지원이 여럿」 |
| R-V8 | 승인 직전 검사 전에는 대기 중인 지원을 미리 거절하지 않는다 | 공고 2.4 「승인 직전」 |

## 4. 마감과 배정

| 번호 | 요구사항 | 출처 |
| --- | --- | --- |
| R-C1 | 관리자가 "모집 마감"을 누른다. 그 뒤로는 지원과 투표를 할 수 없다 | 공고 2.5-1 |
| R-C2 | 마감 때 대기 중인 지원은 거절된다 | 공고 2.5-2 |
| R-C3 | 마감 때 1명뿐인 팀의 학생은 팀에서 빠져 "팀이 없는 학생"이 된다 | 공고 2.5-2 |
| R-C4 | 마감 결과(대기 지원 거절, 1명 팀 학생이 빠짐)는 관리자 화면의 `unassigned`(팀이 없는 학생 표시)에서 확인할 수 있다. `unassigned`에는 팀이 없는 학생의 이름을 보인다 | 공고 2.7 아래 설명 |
| R-G1 | 관리자가 "AI 배정"을 누르면 앱이 AI에게 지금의 팀 구성, 팀이 없는 학생과 그 역할, 2.3절의 규칙을 보내 배정안을 받는다 | 공고 2.5-3 |
| R-G2 | AI는 오픈라우터의 텍스트 생성 모델을 쓴다 | 공고 2.5-3, 4.3 |
| R-G3 | 배정은 팀이 없는 학생만 팀에 넣으며, 이미 팀에 있는 학생은 옮기지 않는다 | 공고 2.5-3 |
| R-G4 | 앱이 배정안을 다섯 가지로 검사한다: ① 팀이 없는 학생이 빠짐없이 배정됨 ② 한 학생은 한 팀에만 배정됨 ③ 모든 팀이 2~4명 ④ 팀 안에서 주 역할 중복 없음 ⑤ 필수 포함 역할 충족 | 공고 2.5-4 |
| R-G5 | AI가 응답하지 않거나, 빈 응답이나 오류를 내거나, 배정안이 R-G4 검사를 통과하지 못하면, 자동으로 2차 모델, 3차 모델 순으로 다시 배정한다 | 공고 2.5-5 |
| R-G6 | 모델 하나를 부른 때부터 응답을 받을 때까지 120초가 넘으면 끊고 다음 모델로 넘어간다 | 공고 2.5-5, 3장 「AI 응답이 늦을 때」 |
| R-G7 | 3차 모델까지 실패하면 앱이 스스로 배정한다 | 공고 2.5-6, 3장 「3차 모델까지 실패」 |
| R-G8 | 검사를 통과한 배정안만 관리자에게 보여 준다(학생의 이름과 역할, 배정된 팀) | 공고 2.5-7 |
| R-G9 | 관리자가 확정하면 DB에 저장한다 | 공고 2.5-7 |
| R-G10 | 규칙을 모두 지키는 배정이 없으면 배정안을 만들지 않고 `assign_status` 안에 "규칙을 지키는 배정이 없음"과 그 이유(예: 팀3에 웹 프로그래머를 맡을 학생이 없음)를 보여 준다. 이때는 AI를 부르지 않아도 된다 | 공고 2.5-8, 2.7 아래 설명 |
| R-G11 | AI를 기다리는 동안 몇 차 모델의 응답을 기다리는 중인지 보여 준다(어려운 해결을 고른 경우) | 공고 3장 「AI 대기 중 화면」 |
| R-G12 | AI 배정이 10분 넘도록 끝나지 않으면 안 된다(전체 대기 시간 제한이 있어야 한다) | 공고 6.3-18 |
| R-G13 | 무료 모델로 자동 연결하는 라우터 `openrouter/free`는 쓰지 않는다. 모델 3개를 이름으로 정한다 | 공고 4.3, 6.3-14 |
| R-G14 | 빈 응답도 실패로 처리한다. 빈 응답을 줄이려고 reasoning effort를 low로 주고 `max_tokens`를 넉넉히 준다 | 공고 4.3 |

## 5. 그 밖에 함께 지켜야 할 요구사항

## 6. 공고에서 정하지 않아 앱이 정한 것

공고에 적히지 않은 부분. 채점은 결과 안내의 첫 단어만 보므로 아래 선택은 점수에 영향이 없도록 골랐다.
다르게 하고 싶은 것이 있으면 구현 전에 고친다.

| 번호 | 정할 것 | 앱의 선택 | 이유 |
| --- | --- | --- | --- |
| D-1 | 막힘 이유가 여럿 겹칠 때 어떤 이유를 보이나 | 마감 → 이미 팀이 있음 → 결과를 기다리는 지원이 있음 → 팀이 꽉 참 → 같은 주 역할 → 필수 포함 역할 자리 순으로 검사해 처음 걸린 이유를 보인다 | 학생 자신의 상태가 팀 상태보다 먼저다. 첫 단어는 모두 "막힘"이다 |
| D-2 | 승인 직전 검사에서 거절될 때의 이유 문구 | `거절: 승인 직전 검사에서 같은 주 역할의 팀원이 있음`처럼 막힘 이유를 그대로 붙인다 | 공고 부록 3의 8단계가 "거절(승인 직전 검사)"로 적혀 있다 |
| D-3 | 찬성·거부 단추를 누를 수 있는 사람 | 그 지원의 팀에 지금 속한 학생 가운데 아직 그 지원에 투표하지 않은 사람 | R-V1, R-V5 |
| D-4 | 새 팀원이 들어오면 이미 쌓인 다른 팀원의 찬성은 어떻게 되나 | 그대로 둔다. 승인은 "지금의 팀원 모두가 찬성했는가"로 판정하므로 새 팀원의 찬성도 필요해진다 | R-V1 |
| D-5 | 마감 뒤 빈 팀(0명)은 어떻게 하나 | AI 배정에서 2명 이상을 채워야 할 팀으로 다룬다 | R-T2 "빈 팀 없음" |
| D-6 | 배정안을 어디에 두었다가 확정하나 | 관리자 세션에 두고, 확정할 때 DB의 지금 상태로 R-G4 검사를 한 번 더 한 뒤 저장한다 | 배정안을 받은 뒤 DB가 바뀌었을 수 있다 |
| D-7 | 관리자도 지원할 수 있나 | 아니다. 관리자에게는 학생 화면(지원, 투표)을 보이지 않는다 | 관리자는 명단에 없다 |

## 7. 받아들임 기준(연습용 시나리오)

공고 부록의 연습용 시나리오 3개를 위에서부터 직접 해 보고, `result`의 첫 단어가 기대 결과와 같으면 받아들인다.
채점은 난이도가 같은 다른 시나리오로 하므로(학생 8~16명, 팀 3~4개, 이름·역할·순서가 다름), 시나리오에 맞춘 코드를
쓰지 않는다. `[공고 6.2-7·8, 부록]`
