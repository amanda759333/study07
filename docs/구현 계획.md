# 구현 계획: 팀 편성 웹 앱

[PRD](PRD.md)의 요구사항을 화면, DB 테이블, 모듈로 나누고, 만드는 순서를 정한다.
요구사항 번호(R-…)는 PRD의 번호다.

---

## 0. 고를 해결 방법(공고 3장)

기능마다 쉬운 해결과 어려운 해결 가운데 하나를 고른다. 교수님 자료 「작업 순서와 프롬프트」 2절의 우선순위(점수 차이가 큰 것부터)를
따르고, 이 계획은 **모두 어려운 해결**을 고른다. 교수님 판단에서 "반드시"·"권장"인 것은 모두 들어 있다.

| 기능 | 점수(쉬운, 어려운) | 차이 | 교수님 판단 | 고른 해결 | 만드는 작업 |
| --- | --- | --- | --- | --- | --- |
| 필수 포함 역할을 지킬 수 없는 팀 | 1.5, 7 | 5.5 | 반드시 어려운 해결 | 지원 단계에서 자리가 모자라게 되는 지원을 막음 | #14 |
| 3차 모델까지 실패 | 0, 6.5 | 6.5 | 시간 남으면 구현 | 검사 5가지를 통과하는 배정을 모든 경우를 따져 찾음(#13에서 만든 탐색을 다시 씀) | #14 |
| 같은 팀에 대기 중인 지원이 여럿 | 0, 3 | 3.0 | 어려운 해결 권장 | 승인 직전 재검사, 투표가 끝난 순서로 처리 | #14 |
| 다른 사람의 변경 보기 | 0.5, 1 | 0.5 | 쉬운 해결도 무방 | `st.fragment(run_every=3)`로 3초마다 자동 갱신. `refresh` 단추는 두지 않음 | #14 |
| AI 응답이 늦을 때 | 0.5, 1 | 0.5 | 어려운 쪽이 안전 | 모델마다 120초 전체 대기 시간을 재서 끊음 | #11 (교수님 #11 프롬프트에 들어 있음) |
| AI 대기 중 화면 | 0.5, 1 | 0.5 | 어려운 쪽이 거의 공짜 | 몇 차 모델을 기다리는 중인지 `assign_status`에 보임 | #11 (교수님 #11 프롬프트에 들어 있음) |
| 마지막 자리에 두 명 동시 진입 | 0, 0.5 | 0.5 | 어려운 해결 권장 | `tf_members` 유일성 제약 | #5 (끝남) |
| DB 일시정지 방지 | 0, 0.5 | 0.5 | 쉬운 해결이라도 반드시 | GitHub Actions 예약 작업으로 매일 DB 질의 + 마감 날(11/2) 배포 앱 직접 사용 | #19 |

`refresh` 단추를 두지 않는 이유: 공고 2.7절 표는 새로 고침 단추를 「다른 사람의 변경 보기」를 **쉬운 해결로 만든 앱만** 두라고 한다.
이 앱은 어려운 해결(자동 갱신)을 했으므로 공고와 똑같이 두지 않는다. 채점 프로그램은 단추가 나타나기를 7초까지 기다리고,
자동 갱신은 3초마다라 그 안에 다른 사람의 변경이 보인다(브라우저에서 3.7초 안에 보이는 것을 확인). `[공고 2.7]`

## 1. 화면

`streamlit_app.py` 한 파일이 세 화면을 그린다. 로그인 여부와 관리자 여부로 고른다.
key는 `CLAUDE.md`의 key 표와 한 글자도 다르면 안 된다.

### 1.1 로그인 화면

| 요소 | key | 비고 |
| --- | --- | --- |
| 학번 입력칸 | `login_student_no` | `st.form` 안 |
| 비밀번호 입력칸 | `login_password` | `type="password"` |
| 로그인 단추 | `login_submit` | `st.form_submit_button` |
| 결과 안내 | `result` | 틀리면 `막힘: 학번 또는 비밀번호가 틀림` |

### 1.2 학생 화면

위에서 아래로:

1. `whoami`: 이름, 학번, 주 역할, 보조 역할, 로그아웃 단추
2. 여기부터 끝까지 `st.fragment(run_every=3)`로 3초마다 자동 갱신(`refresh` 단추는 두지 않음, 0절)
3. `result`: 마지막으로 누른 단추의 결과. 지원·투표 단추가 이 갱신 부분 안에 있으므로 `result`도 안에 둔다
4. 내 상태: "내 팀: 팀2" 또는 "아직 팀이 없음", 결과를 기다리는 내 지원
5. 팀 목록: 팀마다 `team_{n}` 컨테이너 안에
   - 팀 이름과 "내 팀" 표시, 인원 `2/4`
   - 팀원마다 이름, 주 역할, 보조 역할
   - `apply_{n}` 단추. R-X7의 경우(이미 팀이 있음, 결과를 기다리는 지원이 있음, 마감)에는 비활성화
   - 내 팀이면 대기 중인 지원 목록. 지원마다 지원자 이름·역할, 찬성 수/팀원 수,
     `vote_yes_{학번}` `vote_no_{학번}` 단추. 이미 투표했으면 단추 대신 "내 투표: 찬성"

지원 단추를 누르면 `result`에 그 지원의 결과를, 찬성·거부를 누르면 그 지원의 지금 상태를 보인다. `[R-X4, R-X5]`

| 동작 | `result` 예 |
| --- | --- |
| 빈 팀에 지원 | `승인: 팀1에 들어감` |
| 팀원이 있는 팀에 지원 | `대기: 팀원 2명의 투표를 기다림` |
| 막힌 지원 | `막힘: 같은 주 역할의 팀원이 있음` |
| 찬성(아직 남음) | `대기: 2명 가운데 1명 찬성` |
| 찬성(마지막 찬성, 검사 통과) | `승인: 학생7이 팀1에 들어감` |
| 찬성(마지막 찬성, 검사 실패) | `거절: 승인 직전 검사에서 같은 주 역할의 팀원이 있음` |
| 거부 | `거절: 팀원이 거부함` |

### 1.3 관리자 화면

| 영역 | 요소와 key |
| --- | --- |
| 머리 | `whoami`, `result` |
| 명단 올리기 | `admin_roster_file`(`st.file_uploader`), `admin_team_count`(`st.number_input`, 1~20), `admin_start` |

## 2. DB 테이블

공고 5장의 최소 참고안 7개 테이블을 그대로 쓴다. 모두 `schema.sql`에 남긴다. `[R-X13, R-X14]`

| 테이블 | 열 | 제약 |
| --- | --- | --- |
| `tf_students` | `id`, `student_no`, `name`, `main_role`, `password_hash`, `is_admin` | `student_no` 유일, `main_role`은 6개 역할 check(관리자는 null) |
| `tf_student_sub_roles` | `student_id`, `role` | 기본 키 `(student_id, role)`, `role`은 6개 역할 check |
| `tf_teams` | `id`, `name` | `name` 유일 |
| `tf_members` | `team_id`, `slot_no`, `student_id` | 기본 키 `(team_id, slot_no)`, `student_id` 유일, `slot_no between 1 and 4` |
| `tf_applications` | `id`, `team_id`, `student_id`, `status`, `reason`, `created_at` | `status in ('대기','승인','거절')` |
| `tf_votes` | `application_id`, `voter_id`, `vote` | 기본 키 `(application_id, voter_id)`(R-V5), `vote in ('찬성','거부')` |
| `tf_settings` | `key`, `value` | 기본 키 `key`. 행 `closed` = `true`/`false` |

참고안에 없는 것은 앱이 맡는다:

- 팀 번호(`team_{n}`, `apply_{n}`의 n): 명단을 올릴 때 팀을 팀1, 팀2, … 순서로 만들므로 `tf_teams.id` 순서의 번호
  (`row_number() over (order by id)`)로 정한다. 명단을 다시 올리면 `id`는 이어서 커지지만 순서 번호는 1부터다
- 한 학생의 대기 지원은 하나만(R-A3): `service.apply`가 잠금 안에서 확인한다
- AI 호출 기록(README 7.1-5의 근거): 화면 캡처와 앱 로그로 남긴다. 로그에 키나 DB 주소는 넣지 않는다

보안: 모든 `tf_` 테이블에 정책 없이 RLS만 켠다. 앱은 `DATABASE_URL`로 직접 접속하므로 영향이 없고,
Supabase Data API(anon 키)로는 비밀번호 해시를 포함해 아무것도 읽을 수 없게 된다.

동시성: 지원, 투표, 마감은 한 트랜잭션에서 하고, 시작할 때 `tf_settings`의 `closed` 행과 그 팀의 `tf_teams` 행을
`FOR UPDATE`로 잠근다. 같은 팀의 지원·투표가 차례로 처리되고, 마감과 투표가 엇갈리지 않는다. 그래도 겹치면
유일성 제약이 막고, 앱은 그 오류를 `막힘: 팀이 꽉 참` 등으로 바꿔 보인다. `[R-X11]`

## 3. 모듈

```
streamlit_app.py        화면만. service의 함수를 부르고 결과를 그린다
teamform/
  config.py             비밀 값 읽기(.env → st.secrets). 값은 돌려주되 출력하지 않음. 있음/없음 확인 함수
  db.py                 연결 풀(st.cache_resource로 한 번만 만듦), 트랜잭션 도우미, 질의 함수
  rules.py              규칙 판정. DB를 모르는 순수 함수
  solver.py             모든 경우를 따지는 배정 탐색, 배정이 없을 때 이유 찾기
  ai.py                 오픈라우터 호출, 1→2→3차, 모델마다 120초, 응답 해석
  service.py            로그인, 명단 올리기, 지원, 투표, 마감, 배정, 확정. 트랜잭션 안에서 db와 rules를 묶음
schema.sql
tests/
  test_rules.py         rules 단위 테스트(연습 시나리오의 판정을 예시로)
  test_solver.py        solver 단위 테스트
  test_scenarios.py     연습 시나리오 3개를 service로 처음부터 끝까지(DB 필요)
  test_keys.py          AppTest로 화면 key가 표와 같은지
```

### 3.1 `rules.py`의 함수

| 함수 | 하는 일 | 요구사항 | 만드는 작업 |
| --- | --- | --- | --- |
| `check_apply(state, applicant, team)` | 지원 단추를 눌렀을 때 판정. 마감 → 이미 팀 → 대기 지원 → `check_join` | R-A3~R-A7, PRD D-1 | #9 |
| `check_join(team_members, applicant)` | 넣어도 되는지 판정. 정원 → 주 역할 중복. 통과면 `None`, 아니면 이유 | R-A4, R-A5 | #9 |
| `vote_outcome(members, votes)` | 지금 팀원 기준으로 거절/대기/승인 후보 판정 | R-V1~R-V4 | #9 |
| `required_filled(members)` | 팀원 가운데 서로 다른 두 사람에게 기획자·웹 프로그래머를 맡길 수 있는 최대 수(0~2). 기획자 후보와 웹 프로그래머 후보의 이분 매칭 | R-T4, R-T5, PRD 2.1 | #12 |
| `check_assignment(teams, unassigned, plan)` | 배정안 검사 5가지. 어긴 항목을 모두 돌려줌 | R-G3, R-G4 | #12 |
| `check_join`에 필수 포함 역할 자리 더하기 | 정원 → 주 역할 중복 → 필수 포함 역할 자리 | R-A8 | #14 |
| 승인 직전 재검사 | 모두 찬성했을 때 `check_join`을 다시 불러 어기면 거절 | R-V6~R-V8 | #14 |

필수 포함 역할 자리 계산(R-A8): `4 - (지원자를 넣은 인원) < 2 - required_filled(지원자를 넣은 팀원)`이면 막는다.

### 3.2 `solver.py`

- 팀이 없는 학생은 많아야 8명이고 팀은 3~4개다(공고 6.2-8·9). 학생을 하나씩 팀에 넣어 보는 백트래킹으로 모든 경우를 따진다.
  가지치기: 정원 초과, 주 역할 중복, 남은 학생으로 채울 수 없는 필수 포함 역할·최소 인원
- 같은 함수로 (1) AI를 부르기 전에 배정이 있는지 확인하고 (2) 3차까지 실패했을 때 배정을 만든다
- 배정이 없으면 이유를 찾는다: 팀마다 "기존 팀원 + 넣을 수 있는 학생" 가운데 기획자·웹 프로그래머 후보가 있는지,
  인원 합이 맞는지(팀이 없는 학생 수가 채워야 할 최소 인원보다 적거나 남은 자리보다 많음). 짚이는 이유가 없으면
  `모든 경우를 따져도 규칙을 지키는 배정이 없음`

### 3.3 `ai.py`

- 모델 3개를 이름으로 정해 상수로 둔다(`:free` 모델 권장, `openrouter/free` 금지). 2026-10-20 시험 호출로 고른 모델:

  | 차례 | 모델 | 시험 결과(2026-10-20) |
  | --- | --- | --- |
  | 1차 | `nvidia/nemotron-3.5-super-vl:free` | 10/31 실제 배정 문제(부록 중간, 8명) 검사 다섯 가지 통과, 31.5초 |
  | 2차 | `dots-studio/dots-3-note-preview:free` | 10/20 성공 6.9초 → 10/31 실제 배정 문제 통과, 109초 |
  | 3차 | `google/gemma-4-31b-it:free` | 10/20 성공 12.0초 → 10/21·10/31 HTTP 429(사용량 제한) |

  2026-10-31에 순서를 고침. 10/21의 순서는 1차 gemma, 2차 minimax, 3차 dots였으나
  gemma는 계속 HTTP 429였고, minimax는 오픈라우터 무료 모델 목록에서 사라져 HTTP 404가 됨.
  같은 날 시험한 다른 후보: `xingchen-agi/xing4.0-29b-a4b:free` HTTP 429, `recursive/flint-v1.0:free` HTTP 503

  제공사를 나눈 이유: 한 제공사가 막히거나(HTTP 429) 내려가도 다음 모델은 살아 있게 하려는 것이다.

  뺀 모델:
  - `nvidia/nemotron-3-super-120b-a12b:free`(처음 1차 후보): 두 번 모두 HTTP 404(제공사 오류)
  - `google/gemma-4-26b-a4b-it:free`: HTTP 429(제공사 쪽 사용량 제한). 1차와 제공사가 같기도 함

  무료 모델은 날마다 사정이 바뀌므로 #11과 마감 날(11/2)에 다시 시험한다. 그때 공고 예시 모델(`nemotron-3-super`)이 살아 있으면 1차로 되돌릴지 정한다
- 요청: 지금의 팀 구성, 팀이 없는 학생과 역할, 2.3절 규칙 원문, JSON 형식 지시(`{"assignments":[{"student_no":"…","team_no":1}]}`).
  `reasoning: {"effort": "low"}`, `max_tokens` 넉넉히 `[R-G14]`
- 시간 제한: 요청을 작업 스레드에서 보내고, 화면 쪽은 1초마다 `assign_status`의 안내를 고치며 지난 시간을 잰다.
  120초가 되면 기다리기를 그만두고 다음 모델로 간다. 응답이 천천히 와도 전체 시간을 재므로 120초를 넘기지 않는다 `[R-G6, R-G11]`
- 실패로 보는 경우: 시간 초과, HTTP 429, 그 밖의 HTTP 오류·예외, 빈 응답, JSON을 못 읽음, `check_assignment` 실패 `[R-G5]`
- 시도마다 몇 차 모델, 결과(성공, 시간 초과, 빈 응답, HTTP 429, 오류, 검사 실패), 걸린 시간을 `assign_status`와 앱 로그에 남긴다. 오류 문구에 키나 DB 주소가 섞이지 않게 상태 코드와 짧은 설명만 쓴다 `[R-X12]`
- 최대 대기는 120초 × 3 + 앱 배정(1초 안쪽)이므로 10분 제한 안이다 `[R-G12]`

### 3.4 `service.py`의 흐름

| 함수 | 트랜잭션 안에서 하는 일 |
| --- | --- |
| `ensure_admin()` | 앱이 시작할 때 한 번. `admin` 계정이 없으면 만들고, 해시가 `ADMIN_PASSWORD`와 다르면 갱신 `[R-U13]` |
| `login(no, pw)` | bcrypt 비교. 실패면 이유를 하나로 뭉뚱그림 `[R-U17]` |
| `reset_roster(csv_bytes, team_count)` | CSV 검사(열, 역할, 보조 역할 2개 이하, 학번 중복, `admin` 금지) → 관리자 말고 모두 지움 → 학생·보조 역할·빈 팀 생성 → `closed=false` `[R-X1, R-X2, R-U14]` |
| `apply(student, team_no)` | 잠금 → `check_apply` → 막힘이면 기록 없이 이유 반환 / 빈 팀이면 `승인` 지원 행 + 팀원 행 / 아니면 `대기` 지원 행 |
| `vote(voter, applicant_no, yes)` | 잠금 → 투표자가 지금 팀원이고 아직 안 했는지 확인 → 투표 행 → 거부면 `거절` / 모두 찬성이면 `check_join` 재검사 후 `승인`(팀원 행) 또는 `거절` |
| `close()` | 잠금 → `closed=true` → 대기 지원 모두 `거절`(이유: 모집 마감) → 1명 팀의 팀원 행 삭제 `[R-C1~R-C3]` |
| `propose()` | 마감 확인 → `solver`로 배정 존재 확인(없으면 이유) → `ai`로 1~3차 → 모두 실패면 `solver`의 배정 |
| `confirm(plan)` | 지금 DB로 `check_assignment` 다시 → 팀원 행 삽입 `[R-G9, PRD D-6]` |

### 작업별 주의

- **#6**: DB 연결은 처음부터 `st.cache_resource`로 한 번만 만들어 다시 쓴다(`CLAUDE.md` 코딩 규약). #15의 "DB 연결 재사용"은 점검만 한다
- **#9**: 이 작업에서는 기본 규칙(빈 팀 바로 승인, 정원, 주 역할 중복, 한 번에 한 팀, 이미 팀 있음, 마감, 한 명 거부 → 거절, 투표는 투표하는 때의 팀원)만 만든다.
  필수 포함 역할 자리와 승인 직전 재검사는 교수님 순서대로 #14에서 더한다. 그래서 #9의 확인에서 어려움 8·11단계는 뺀다
- **#9**: 빈 팀 지원은 투표 없이 바로 팀원 행까지 넣는다. 막힘은 DB에 쓰지 않는다

- **#14**: 승인 직전 검사는 "투표가 끝난 순서"로 처리한다. 대기 중인 지원을 미리 거절하지 않는다 `[R-V7, R-V8]`.

  key는 다시 그릴 때마다 같아야 한다
- **#17**: 배포 화면의 Branch 칸은 지금 브랜치 이름(`master`)을 넣는다. 채점 기간(11/3~11/4)에는 관리자 비밀번호를 바꾸지 않는다 `[공고 6.3-17]`
- **모든 작업**: 시나리오 이름·순서·학생 이름을 보고 분기하는 코드를 쓰지 않는다 `[R-X16]`. 클로드가 틀린 것을 찾으면
